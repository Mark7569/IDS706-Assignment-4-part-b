**1. Requirements and goals**

- Generate reproducible tables, plots, and model evaluation results.

Treat 2015–2025 as the intended study period. Verify actual coverage before describing the dataset as covering those years.

**4. Data analysis approach**

Use the following sequence:

1. **Inspect the input.** Record row count, columns, data types, date range, missingness, duplicate dates, and basic numeric summaries.
2. **Validate and clean.** Parse dates using a documented format, require the expected columns, sort chronologically, and reject invalid dates and nonfinite numeric values. Report any rows excluded.
3. **Handle duplicates explicitly.** Remove exact duplicate rows with a recorded count; reject conflicting records for the same date until a resolution rule is agreed upon.
4. **Produce descriptive results.** Calculate yearly GLD means with observation counts, and return rows where `GLD > 200`. Represent years without observations as missing rather than zero.
5. **Visualize results.** Produce a GLD time series, yearly-average chart, and held-out actual-versus-predicted plot.
6. **Model GLD.** Use `SPX`, `USO`, `SLV`, and `EUR/USD` as predictors. Reserve the latest portion of the data for testing, with no random shuffling.
7. **Evaluate results.** Report MAE, RMSE, and R² where defined. Compare regression against a baseline that predicts the training-set mean GLD.
8. **Save an audit record.** Include input checksum, configuration, date ranges, row counts, excluded-row counts, and metrics.

For missing values, I recommend excluding missing GLD values from calculations requiring GLD and reporting those exclusions. For model predictors, use a median imputer fitted only on training data. Reject a predictor that is entirely missing in the training set.

A key distinction: predicting GLD from other prices on the **same date** is contemporaneous estimation. It is not future-price forecasting. Genuine forecasting would require a prediction horizon and lagged predictors. For this assignment, I recommend keeping contemporaneous estimation and stating that limitation clearly.

**5. Testing strategy, including edge cases**

Use small synthetic datasets with deliberately chosen values and independently calculated expectations.

| Area | Meaningful checks |
|---|---|
| Loading and validation | Missing file, empty CSV, missing required columns, malformed dates, nonnumeric values, infinity |
| Cleaning | Unsorted dates, exact duplicates, conflicting duplicate dates, missing values, input remains unchanged |
| Yearly summaries | Known means, year boundaries, partial years, missing years, a year with no valid GLD values |
| Threshold filtering | Below 200, exactly 200 excluded, above 200 included, no matches, all matches |
| Model preparation | Training dates strictly precede test dates, GLD excluded from predictors, insufficient observations |
| Leakage prevention | Imputer statistics come only from training data, including when test values have an extreme distribution |
| Evaluation | Known metric values, constant targets, too-small test sets, baseline uses training data only |
| Integration | CLI runs on a fixture and creates readable tables, metrics, and nonempty plots |
| Failure behavior | Invalid configuration and invalid input produce clear errors and a nonzero exit status |

Do not require a particular R² on the real dataset: predictive quality is an analytical result, not a stable software correctness condition. Check plot creation and labeling without brittle pixel comparisons.

**6. Docker/containerization approach**

Use a slim Python base image matching the supported local Python version. Install the package and runtime dependencies from the lockfile, then run the same CLI used locally.

The container should:

- Run as a non-root user.
- Read input from a read-only mounted directory.
- Write results to a separate mounted output directory.
- Use a noninteractive plotting backend.
- Exclude datasets, generated outputs, virtual environments, and Git history from its build context.

Document one build command and one run command. A separate test stage can install development dependencies and run tests without including those tools in the final runtime image. Docker Compose is unnecessary for this single-process project.

**7. Risks and design concerns**

- **Dataset coverage:** Confirm that the file actually spans 2015–2025 and identify partial years or gaps.
- **Meaning of GLD:** Verify whether GLD represents an ETF price and whether it is adjusted. Do not describe it as the spot price of gold without evidence.
- **Calendar alignment:** Different markets may have different trading days. Avoid filling absent dates automatically.
- **Leakage:** Chronological splitting and training-only preprocessing are essential.
- **Misleading averages:** Yearly means describe observed records; missing periods can bias comparisons.
- **Regression limitations:** Correlated financial predictors and changing market relationships can make coefficients and predictions unstable.
- **Reproducibility:** Dependency locks need to be paired with a stable dataset, recorded configuration, and a supported Python version.
- **Scope:** Keep the initial design small; a database, web service, and complex model registry are unnecessary.

There are two important qualifications.

First, contemporaneous regression on price levels needs restrained interpretation. Prices can move together because of shared trends, and correlated predictors can make individual coefficients unstable. A chronological holdout helps assess performance on later observations, but neither a strong fit nor that holdout establishes economic causation. Report associations, residual errors, and limitations.

Second, forecasting needs a stronger baseline: **predict tomorrow’s GLD as today’s GLD**. A next-day regression can produce impressive-looking price predictions simply because adjacent prices are similar. Its useful contribution is whether it improves on that persistence baseline on unseen dates, not whether its R² looks high.

If you chose forecasting, I would define the task as: “After the relevant markets close on trading day *t*, predict GLD for the next trading day.” Include current GLD as an available predictor, explicitly align each target to the following trading session, and verify that “next row” actually means “next trading day.” Training labels must also be available before the first test forecast is issued.

For the initial course submission, keep contemporaneous regression, use a chronological holdout, fit preprocessing only on training data, and compare against the training-mean baseline. Call it **“GLD relationship analysis with contemporaneous linear regression.”** Document next-day forecasting as a possible extension.
